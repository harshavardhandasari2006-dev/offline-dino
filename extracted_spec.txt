1. Executive Summary
OFFLINE DINO is an existing offline-first, no-ads endless-runner game inspired by the Chrome Dino concept. The project already has an approved colorful 2D cartoon dinosaur and a mostly completed interface. This is targeted improvement, not a redesign.
The work covers three areas, in this order:

1
Home Page cursor interactions:  natural pupil tracking, subtle head movement, expressions, blinking, and a small playful click reaction.

2
Skin-selection rotation:  preserve the existing skin UI and make the exact original dinosaur turn smoothly through front, left, right, back, and intermediate views where supported by available artwork.

3
Running animation:  correct leg coordination, ground contact, body rhythm, tail movement, framing, and animation timing as game speed increases. Difficulty must increase gradually and fairly.
The overall visual style remains 2D cartoon. \2233D\224 means convincing turning and natural movement\227not a realistic 3D dinosaur. Matched 2D views or cartoon-style 2.5D techniques may be used if more reliable than continuous model rotation.

Success means: the three areas look and behave correctly, the original character remains consistent, existing gameplay continues to work, and every completion claim is supported by real test results.
2. Scope, Priorities, and Non-Negotiable Rules
2.1 Work order

Order
Area
Main outcome
1
Home Page cursor interactions
Responsive, natural, stable cursor-driven character behavior.
2
Skin-selection rotation
Smooth, accurate turning with consistent character design across skins.
3
Running animation
Natural running cycle, correct framing, speed synchronization, and fair difficulty progression.
2.2 Mandatory constraints
\177 Keep the game 2D cartoon. Do not replace the approved dinosaur with a realistic 3D model or a different generic dinosaur.
\177 Preserve the original proportions, silhouette, face, eyes, cream belly, outlines, highlights, shading, claws, tail shape, and defining details.
\177 Keep the existing Home Page and skin-selection UI substantially unchanged.
\177 Keep green as the default skin. Other skins change the intended skin color only; protected details must remain correct.
\177 Do not expand the work into unrelated features, screen redesigns, or gameplay systems.
\177 Preserve working features and fix regressions caused by these changes.
\177 Use explicit instructions and observable acceptance checks instead of vague words such as \223smoother.\224
\177 Never claim a fix, test, screenshot, or result exists unless it is genuinely available.
2.3 Explicitly out of scope
Do not redesign the Home Page, rebuild the skin-selection UI, add new gameplay features, change unrelated screens, or modify broader gameplay systems. Day/night transition work is a separate topic and is not included here.

3. Required Workflow Before Editing
Antigravity must complete the following steps before modifying project files. The selected approach is to work directly in existing files without creating a separate backup first. This does not remove the obligation to inspect carefully and preserve working behavior.
3.1 Inspect the full project
Review the project structure and relevant source files, including Home Page, skin selection, character assets, sprite sheets, animation logic, input handlers, and gameplay speed/difficulty logic.
3.2 Trace dependencies
Identify how components, animation states, sprites, skin colors, and gameplay speed depend on one another. Record shared code that could affect multiple priorities.
3.3 Inventory original assets
Locate the approved gameplay dinosaur, original sprite sheets, animation frames, skin assets, and existing screenshots. Record paths and usage.
3.4 Establish a baseline
Run the current game and reproduce known issues before editing. Record observations and capture genuine screenshots or short recordings where possible.
3.5 Diagnose root causes
For each defect, state the symptom, likely or confirmed cause, relevant files, and proposed fix. Mark a cause \223suspected\224 until verified.
3.6 Map changes to requirements
List expected files to change and link each change to a requirement ID in Section 10. Avoid edits outside scope.
3.7 Implement in agreed order
Complete and test Home Page interactions, then skin rotation, then running animation. Explain any dependency that requires changing this order.
3.8 Test each area
Test and correct each area before proceeding to the next.
3.9 Integrate and regression-test
After all three areas work individually, test them together and verify existing gameplay features in Section 9.
3.10 Report honestly
Produce the evidence-based report in Section 11. Use Pass, Fail, or Unverified for each requirement.

Editing rule: Prefer targeted changes. Refactor larger sections only when justified by the root cause; explain significant refactoring and test it for regressions.

4. Priority 1 \227 Home Page Cursor Interactions
Goal: make the dinosaur feel like a responsive cartoon character while keeping the body stable and preserving the approved design. These interactions apply to the Home Page only; do not add them to gameplay unless already required.
4.1 Required cursor behavior

Cursor situation
Expected behavior
Cursor far away / not interacting

Pupils respond almost immediately; head turns naturally left. Body stays stable.
Cursor moves right
Pupils respond almost immediately; head turns naturally right. Body stays stable.
Cursor at horizontal center

Cursor moves upward

Pupils follow downward; head may bend subtly down.

Player clicks/touches dinosaur
Small cute startled wiggle or playful reaction; a small whole-body motion is allowed, then returns smoothly.
Cursor leaves / moves far away
Finish expressions naturally and return smoothly to idle.
4.2 Movement and appearance rules
\177 Pupils respond quickly enough to feel connected to cursor movement, with enough smoothing to prevent jitter.
\177 Head movement and pupil movement stay synchronized; the head must not noticeably lag behind the eyes.
\177 Left/right turns show clear side profiles; center/front view shows both eyes clearly.
\177 Preserve exact in-game pupil size and eye appearance, including white sclera and black pupils. No flickering or color changes.
\177 Keep body shape stable during tracking and smiling. No stretching, flattening, widening, or unnatural narrowing.
\177 Preserve the approved design during blinking, smiling, and click reactions.
\177 Use smooth transitions rather than switching between only a few static poses. A rig or detailed frame sequence is acceptable if design fidelity is preserved.
\177 Do not allow click, blink, smile, and head turn to conflict or overlap visibly.
4.3 Animation priority and state handling
Use a coordinated animation-state system or equivalent reliable method. In simple terms, the character should know which behavior is active and how to transition to another behavior.

State / interaction
Required handling
Idle
Default state when no active cursor reaction is needed.
Tracking
Pupils and head respond to cursor position without unnecessary body movement.
Smile / blink
Blend naturally with tracking; avoid facial distortion or abrupt resets.
Click reaction
Has suitable priority; smoothly interrupts compatible actions without conflicting head or facial movement.
Return to idle/tracking
When the reaction ends, restore the correct state based on the current cursor position.
4.4 Acceptance checks
\177 Move cursor slowly and rapidly in all directions; verify response without jitter or visible delay.
\177 Move cursor left, right, center, top, and bottom; check side profiles, forward view, and vertical tracking.

5. Priority 2 \227 Skin-Selection Rotation and Skin Consistency
Goal: preserve the existing skin-selection interface and make the original dinosaur turn smoothly and consistently. A smoothly rotating generic dinosaur is not acceptable; rotation must use the approved character design.
5.1 Rotation behavior
\177 Preserve the existing rotation controls and UI.
\177 Support front, left, right, and back directions plus intermediate views where available.
\177 Test slow input, fast input, reversing direction, repeated input, stopping midway, and resuming.
\177 Prevent sudden snapping, skipped views, flickering, visible gaps, inconsistent outlines, or changes to body proportions.
\177 Allow rotation to be interrupted and resumed without a broken pose.
\177 If current artwork cannot support reliable continuous rotation, use carefully matched 2D views and intermediate frames rather than an inaccurate invented model.
5.2 Preserve character proportions and facial features
\177 Use original gameplay dinosaur and original sprite/animation frames as equally important references.
\177 Check front, left, right, back, and intermediate views against silhouette, head size, body length, belly shape, tail, feet, and claws.
\177 Allow natural perspective only if it does not make the character appear stretched, flattened, or changed in identity.
\177 Preserve eye whites and black pupils, outline thickness, highlights, shading, and facial expression as closely as original assets allow.
\177 Do not substitute a different dinosaur model or make an unapproved redesign.
5.3 Skin behavior
All skins use the same character design. The skin system changes the intended skin color only. The cream belly, eye whites, black pupils, outlines, claws, highlights, shading, facial details, and transparent background must remain correct.

Requirement
Verification
Default skin
Green is selected by default.
Skin color
Each available color is applied consistently without changing character identity.
Protected details
Belly, eyes, pupils, outlines, claws, shading, and highlights remain intact.
Transparency
No white halo, opaque rectangle, or unwanted background around transparent sprites.
Cross-screen consistency
Preview, Home Page, animation frames, and gameplay show the same selected skin.
Rotation consistency
Turning does not change skin colors, erase details, or introduce mismatched frames.
5.4 Acceptance checks
\177 Rotate through every supported direction and intermediate view; inspect for snapping, flicker, gaps, and distortion.
\177 Interrupt rotation, reverse direction, stop midway, and resume.
\177 Test every available skin: green, blue, red, yellow, orange, purple, pink, brown, and charcoal.
\177 Check green default and verify the selected skin appears consistently across relevant screens and animations.
\177 Inspect transparent edges and protected details at normal size and, where useful, enlarged.
\177 Compare each view against original gameplay dinosaur and sprite frames.

6. Priority 3 \227 Running Animation and Difficulty Progression
Goal: repair the existing running cycle first, then add missing frames or improve the animation technique only when needed. The result remains a natural 2D cartoon, not a realistic 3D dinosaur.
6.1 Running cycle requirements
\177 Legs alternate correctly; neither leg may appear frozen, disconnected, or permanently floating.
\177 Feet make believable ground contact. Avoid obvious inconsistent foot sliding.
\177 Body remains coordinated and stable, with a natural cartoon rhythm.
\177 Tail moves gently in coordination with the running rhythm and preserves its original shape and proportions.
\177 Tail must never be clipped by canvas, sprite bounds, viewport, or animation frame.
\177 Correct frame timing, missing/defective frames, and unwanted jumps between poses.
\177 Do not introduce eye flicker, eye color changes, white halos, or unrelated facial distortions.
\177 Review the complete cycle repeatedly at actual gameplay speed and compare with the original dinosaur.
6.2 Tail, framing, and edge handling
The tail shape must remain unchanged. Motion may be gentle and fluid, but it must not swing excessively, stretch, change thickness, or clip. Check the complete silhouette at every frame, including the tail tip and poses that move the body vertically.
If sprite bounds or canvas sizing cause clipping, identify and correct the relevant bounds, padding, frame alignment, or rendering logic. Do not shrink or distort the dinosaur just to hide the problem.
6.3 Animation timing as game speed increases
\177 Synchronize animation playback with gameplay speed while preserving natural cartoon movement.
\177 Test low, medium, and high gameplay speeds. The cycle must not become excessively fast at high scores.
\177 Keep leg motion coordinated with ground contact and tail motion synchronized with the running rhythm.
\177 Avoid sudden jumps in animation speed or timing.
\177 Test the full cycle repeatedly at actual gameplay speed, not only in a paused editor or static preview.
6.4 Gradual difficulty progression
Both dinosaur speed and obstacle frequency should increase gradually with score. The beginning should feel calm; the increase should be almost imperceptible at first, then progressively noticeable at higher scores. Avoid sudden difficulty spikes.
\177 Test at low, medium, and high scores.
\177 Ensure obstacle spacing leaves fair reaction time.
\177 Avoid impossible obstacle combinations or obstacles that become unavoidable solely because speed increased.
\177 Keep dinosaur animation synchronized with movement speed.
\177 Confirm difficulty progression does not cause stuttering or tail/body clipping.
6.5 Acceptance checks
\177 Watch multiple complete running cycles at low, medium, and high speeds.
\177 Confirm both legs alternate and feet contact the ground plausibly.
\177 Check tail in every frame and during vertical movement; no clipping is allowed.
\177 Look for frozen, disconnected, duplicated, or out-of-rhythm frames.

8. Implementation Guidance and Animation-State Coordination
This guidance is technology-neutral. Antigravity should use the existing project architecture unless inspection reveals a clear reason to change it.
8.1 General implementation rules
\177 Identify exact files and components responsible for each requirement before editing.
\177 Reuse existing character assets and animation logic where possible.
\177 Avoid duplicate character definitions or inconsistent versions of the dinosaur.
\177 Keep skin color selection separate from protected details and transparency.
\177 Keep animation state changes explicit and predictable.
\177 Prefer small, testable changes over a large rewrite.
\177 Explain significant refactoring in plain English and list affected files.
8.2 Example Home Page state flow

8.3 Example rotation flow
Rotation input  \256  determine direction and progress  \256  display matching view or interpolate between matching views  \256 keep proportions and protected details consistent  \256  handle interruption/reversal  \256  settle at the requested view. If continuous interpolation causes visual errors, use matched intermediate 2D frames.
8.4 Example running flow
Read gameplay speed  \256  choose an appropriate running-cycle playback rate  \256  advance coordinated leg/body/tail frames  \256  verify ground contact and sprite bounds  \256  repeat without jumps or clipping. Difficulty progression must be gradual and separate from arbitrary animation distortion.
8.5 Avoiding animation conflicts
When a click, blink, smile, cursor movement, or rotation interrupts another animation, the implementation should transition cleanly. Do not let two animations write conflicting values to the same feature at the same time. When an action ends, calculate the correct next state from current input and gameplay context.

9. Performance, Browser, and Regression Testing
Testing must include automated checks where practical and actual browser inspection. Automated tests can verify logic, but do not replace visual inspection of appearance and animation.
9.1 Performance and interaction tests
\177 Test rapid/slow cursor movement, repeated clicks, continuous rotation, reversals, and interruptions.
\177 Test every skin and the full running cycle at low, medium, and high gameplay speeds.
\177 Look for frame drops, stuttering, flickering, memory problems, and animation conflicts.
\177 Fix performance problems without sacrificing the original cartoon design.
\177 Do not invent numeric frame-rate guarantees unless an existing or agreed target provides them. Record the actual test environment and observed result.
9.2 Browser and screen conditions
\177 Test in the current browser at different window sizes and in fullscreen.
\177 Test other supported desktop browsers where available.
\177 Resize the window while animations are running.
\177 Test fullscreen transitions and switching tabs or minimizing the window.
\177 Verify character positioning and animation stability.
\177 Verify existing pause/resume behavior and report environments that could not be tested.
9.3 Required regression checks
Verify these existing features still work after changes. This is a regression check, not permission to redesign them.

Feature
Regression check
Game launch
Game starts without new errors or a broken screen.
Controls
Existing keyboard and mobile controls still behave as before where applicable.
Running / jumping / crouching
Movement works; character does not freeze or distort.

Obstacle behavior and score progression remain functional.
High scores
Existing high-score behavior remains intact.
Pause / resume
Existing pause and resume behavior remains intact.
Game Over
Game-over screen and final character pose remain correct.
Sound
Existing sound behavior remains functional.
Offline operation
Game remains usable without runtime internet access.
Skins
Selected skin remains consistent across preview and gameplay.
9.4 Defect and retest procedure

1
Record the exact defect and reproduction steps.

2
Identify whether it existed before changes or was introduced by them.

3

4
Apply a justified fix and identify changed files.

5
Repeat the failed test and related tests.

6
Run regression checks on potentially affected features.

7
Record Pass, Fail, or Unverified with evidence.
